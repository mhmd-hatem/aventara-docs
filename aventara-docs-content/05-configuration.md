# Configuration

Aventara is configured by one object, usually returned from `src/aventara.config.ts`. Start from the generated file and add to it:

```ts
import { createPrismaAdapter } from "@aventara/prisma7-adapter";
import { discovery } from "./generated/aventara/discovery.artifact.js";
import type { PrismaService } from "./prisma.service.js";

export async function aventaraConfig(prisma: PrismaService) {
  return {
    entrypoint: "/api",
    adapter: await createPrismaAdapter({
      client: prisma,
      discovery,
      provider: "sqlite",
      driver: "@prisma/adapter-better-sqlite3",
    }),
  } as const;
}
```

Keep the `as const`: it lets TypeScript check your `restrictions`, `fields` and `behaviors` against your real Resources and fields. A misspelled Resource or field name is a compile error.

Each block has a task-based guide:

| To... | Read |
|---|---|
| Hide a field, make it write-only or read-only | [Exposing and hiding fields](/docs/exposing-and-hiding-fields) |
| Switch operations off, per layer | [Restricting operations](/docs/restricting-operations) |
| Require sign-in, answer `A4000`/`A4001` | [Authentication and guards](/docs/authentication-and-guards) |
| Validate, transform, audit, wrap or rewrite errors | [Pipelines](/docs/pipelines) |
| Add virtual fields, hash a password, compute a slug | [Computed fields](/docs/computed-fields) |
| Tune limits | [Limits and safety](/docs/limits-and-safety) |
| Give a `Json` field a type that is checked on every write | [JSON fields](/docs/json-fields) |
| Receive the real error behind a failure | [Request IDs and diagnostics](/docs/request-ids-and-diagnostics) |
| Ship it | [Deploying](/docs/deploying) |

## The shape

```ts
type FrameworkConfig = {
  entrypoint: string;              // where the protocol is mounted, e.g. "/api"
  adapter: Adapter;                // from createPrismaAdapter(...)
  diagnostics?: FrameworkDiagnosticsSink;
  misuse?: FrameworkMisuseSink;    // counts server-side calls refused as unreadable or not plain data

  // Root = the default for every layer
  fields?: ...;                    // add virtual scalar fields
  behaviors?: ...;                 // computed field behavior (server-side code)
  restrictions?: ...;              // hide, limit, switch off
  limits?: Partial<ContractLimits>;
  pipelines?: PipelineConfig;      // guards, pipes, hooks, interceptors, filters
  transactions?: "none" | "interactive";

  application?: { /* same blocks, overrides for server-side calls */ };
  client?: { /* same blocks, overrides for remote callers */ };
};
```

### Root and layer overrides

The root is the default. The `application` and `client` blocks override it for one layer. For each property, if a layer sets it explicitly, that value wins; otherwise the root value is used. `false` counts as explicitly set. Define only what differs.

Pipelines are the exception: they are concatenated. Root pipelines run first for every operation, then the layer's own.

## Adapter

`createPrismaAdapter` takes a Prisma client you construct (with a driver adapter) and the `discovery` artifact generated by `aventara:prepare`:

```ts
await createPrismaAdapter({
  client: prisma,
  discovery,
  provider: "postgresql",              // "sqlite" | "postgresql", declared, never sniffed
  driver: "@prisma/adapter-pg",        // or "@prisma/adapter-better-sqlite3"
  transactionOptions: { timeout: 10_000, isolationLevel: "Serializable" }, // optional
});
```

`transactionOptions` (`maxWait`, `timeout`, `isolationLevel`) belong to the adapter and are not part of Aventara's public configuration. The `discovery` artifact is regenerated by `npm run aventara:prepare`; run that whenever your schema changes.

## Entrypoint

`entrypoint` is where the protocol is mounted (`"/api"`, `"/v1/data"`). Routes are relative to it: `GET /api/_contract`, `POST /api/_resources/User/find/many`. It alone decides the mount point; Nest's global prefix does not move it. See [NestJS host](/docs/nestjs-host#entrypoint).

## Restrictions

Restrictions remove or limit what a Resource exposes. Where a field is hidden it disappears everywhere in that layer: inputs, outputs, filters, ordering, identifiers and nested projections.

```ts
restrictions: {
  User: {
    hidden: false,                         // true removes the whole Resource
    fields: {
      passwordHash: {
        // write-only: can be set on create/update, never read, filtered or ordered
        capabilities: { select: false, filter: false, order: false },
      },
      internalNotes: { hidden: true },     // not in this layer at all
    },
    operations: {
      delete: { first: false, unique: false, count: false },   // switch operations off
    },
  },
}
```

| Where | Option | Effect |
|---|---|---|
| Resource | `hidden: true` | The Resource does not exist in this layer. |
| Resource | `operations` | `false` switches a variant off (`find`: `first`, `unique`, `many`, `count`; `create`: `one`, `many`, `count`; `update`: `first`, `unique`, `many`, `count`; `delete`: `first`, `unique`, `count`; `upsert`: `unique`). It can only switch operations off; it cannot redefine them. |
| Field | `hidden: true` | The field does not exist in this layer. |
| Scalar field | `capabilities.select` / `order` / `orderNulls` | `false` forbids reading / ordering. |
| Scalar field | `capabilities.filter` | `false`, or a list of allowed operators such as `["equals", "in"]`. |
| Scalar field | `capabilities.create` / `update` | `false`, or a list of allowed directives (`"$increment"`, `"$push"`, ...). |
| Relation field | `capabilities.select` / `include` / `filter` / `order` / `pagination` / `reducers` / `create` / `update` | Narrow what a relation can do. |

A field that cannot be selected is a write-only field: a request that selects it fails with `A2004` / `V1008` ("Field "passwordHash" is not selectable."). More in [Exposing and hiding fields](/docs/exposing-and-hiding-fields).

Safety rules at startup:

- If you hide a Resource but a relation that points at it stays visible, the framework refuses to start with a `FrameworkConstructionError` (`COMPILER_DANGLING_RELATION`). Hide the relation fields too:

  ```ts
  restrictions: {
    Post: { hidden: true },
    User: { fields: { posts: { hidden: true } } },
  }
  ```
- If a hidden field is part of an identifier, that identifier is dropped. If no identifier remains, the `unique` operations that need one disappear.

### Per-layer restrictions

Restrictions at the root apply to every layer. To restrict only remote callers, put them under `client`:

```ts
client: {
  restrictions: {
    User: { operations: { delete: { unique: false, first: false, count: false } } },
  },
},
```

The contract served at `/_contract` is the client layer, so these removals also remove the methods from the generated frontend client. Regenerate the client afterwards. See [Restricting operations](/docs/restricting-operations).

## Operations availability

Which operations a Resource offers is decided in two steps: the adapter advertises what it can perform, and your `restrictions.<Resource>.operations` switch some off. You can inspect the result in the contract:

```json
"operations": {
  "create": { "count": {...}, "many": {...}, "one": true },
  "delete": { "count": true, "first": true, "unique": true },
  "find":   { "count": true, "first": true, "many": true, "unique": true },
  "update": { "count": {...}, "first": true, "many": {...}, "unique": true },
  "upsert": { "unique": true }
}
```

## Pipelines

Pipelines are server-side callbacks that run around every operation: guards (allow or refuse), pipes (transform arguments), hooks (`before` / `after`), interceptors (wrap execution) and filters (rewrite errors). They never appear in a contract.

```ts
import { FrameworkError, type Guard } from "@aventara/core";

// Refuse every write from remote callers that carries no Authorization header.
const requireSignIn: Guard = (ctx) => {
  if (ctx.family !== "find" && !ctx.transport?.headers["authorization"]) {
    throw new FrameworkError("A4000", "Sign in first.");
  }
  return true;
};

export async function aventaraConfig(prisma: PrismaService) {
  return {
    entrypoint: "/api",
    adapter: /* ... */,
    client: {
      pipelines: { guards: [requireSignIn] },   // remote callers only
    },
  } as const;
}
```

A caller that sends no `Authorization` header gets `A4000` (HTTP 401); the generated client throws `AuthError`.

What a pipeline receives (`PipelineContext`): `origin` (`"application"` or `"client"`), `resource`, `family`, `variant`, `args`, `requestId`, `contract`, and for remote requests `transport.headers` (lower-cased names; repeated headers joined). Guards return `true`/`undefined` to allow, `false` to deny with `A4001` (`FORBIDDEN`), or throw a `FrameworkError` with the code you choose (`A4000` unauthenticated, `A4001` forbidden, `A4002` policy denied). A thrown `A2004` may carry `issues` (`{ path, code, message }`); the path must name a member of the request's arguments, such as `["arguments", "data", "email"]`, and each message reaches the caller as written when it is non-blank and at most 1,000 characters ([Pipelines](/docs/pipelines)).

Authentication and authorization belong in pipelines. Nest guards, interceptors and pipes never run on Aventara routes. See [Authentication and guards](/docs/authentication-and-guards), [Pipelines](/docs/pipelines) and [NestJS host](/docs/nestjs-host#what-runs-on-aventara-routes).

> Typing note: annotate a pipeline callback with its exported type (`Guard`, `Pipe`, ... as above) when you write it in a configuration that a function returns `as const`, or the parameter has no contextual type (`Parameter 'ctx' implicitly has an 'any' type`). The same goes for the `diagnostics` function: annotate it `(d: FrameworkDiagnostic)`. See [Pipelines](/docs/pipelines#typing-a-stage).

## Limits

Limits bound what a caller may ask for:

| Limit | Default | What it bounds |
|---|---|---|
| `maxRequestBytes` | `1048576` | Decoded request body size (`A2010`). |
| `maxNestingDepth` | `12` | Nested projection / relation depth. |
| `maxListLimit` | `250` | The `limit` of a list or nested relation (`A2009` / `V1014`). |
| `maxTransactionOperations` | `20` | Steps in one transaction plan. |
| `maxBooleanNodes` | `50` | Nodes in a `where` boolean tree (`AND`/`OR`/`NOT`). |

```ts
limits: { maxListLimit: 100 },
client: { limits: { maxListLimit: 25 } },
```

Client limits are part of the client contract, so changing them changes its hash. See [Limits and safety](/docs/limits-and-safety).

## Transactions

`transactions: "interactive"` (the default for the Prisma adapter) turns on `POST /_transactions` and the client's `avClient.tx` / `avClient.transaction`. `"none"` turns them off for a layer:

```ts
client: { transactions: "none" },
```

See [Transactions](/docs/transactions).

## Fields and behaviors

`fields` adds virtual scalar fields to a Resource (`defineFields` from `@aventara/core` checks them against your model), and `behaviors` attaches server-side code that computes a field's value on read, create or update, for example a hashed password, a slug or a display name. See [Computed fields](/docs/computed-fields).

## Diagnostics

`diagnostics` is root-only: one function that receives the raw error behind every unplanned failure, with the request id. See [Request IDs and diagnostics](/docs/request-ids-and-diagnostics). Its companion `misuse`, also root-only and optional, receives one event for every server-side call refused because its input could not be read or was not plain data ([Server-side usage](/docs/server-side-usage#what-a-server-side-call-accepts)).
